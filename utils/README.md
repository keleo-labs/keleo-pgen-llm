# Practice Language Utilities

Scripts for validating, inspecting, fixing, and assembling Practice Language JSON files.

## Prerequisites

**Required:** Python 3.9+ (standard library only — no pip packages), `keleo-language` repo at `../../keleo-language/` (provides schema, validators, and semantic references via symlinks)

**Optional tools by feature:**

| Tool | Scripts that use it | Role |
|------|-------------------|------|
| `gws` CLI | `extract-gws-slides.py`, `edit-gws-slides.py`, `edit-gws-doc.py`, `check-gws-slides-fit.py`, `render-gws-slides.py`, `studio-client.py`, `issue-register.py` | Content sourcing from Google Workspace (Slides, Drive), published deck and document editing, and feedback register access (Sheets) |
| Node.js 18+ | `validate-json-schema.js` | Alternative schema validation via ajv-cli |
| Remote bundle repository | `studio-client.py`, `discover-dependencies.py --remote` | Centralised `.keleo` package storage and version management |

## Assessment & Validation

| Script | Purpose | Usage |
|--------|---------|-------|
| `assess-practice.py` | Unified quality assessment: structure, uniqueness, competency levels, cross-references, baseline references, pattern quality (sparse alphas, few views, misaligned states, and `pattern-prerequisites` — a view asserting a state whose prerequisites only a later view reaches, a view declaring one alpha twice, and a state moving backwards, via `check-pattern-prerequisites.py`; the orderings that module names `entry`, `cyclical` and `unreached` are dropped here, being permitted by the language rather than defects); auto-discovers baseline and parent practices from declared dependencies, and warns when a declared dependency cannot be pinned to one file rather than dropping it silently; the paths given to `--parent` are forwarded to `validate-practice-json.py` as well as merged locally, so the two agree on what resolves; `--online` checks asset URLs, citation URLs, reference URIs, and citations missing URLs; `--category` filters to specific issue categories (supports prefix matching, e.g. `pattern` matches `pattern-*`). `narrative-placement` matches on the narrative's **name** only, in step with `fix-common-issues.py` — a top-level narrative whose *description* mentions an element is usually the document's own practice narrative, and flagging it had an agent move a practice narrative onto an alpha. `narrative-context-length` names the offending narrative and element, the way `lod-naming` does, since a bare count over eighty-odd contexts cannot be acted on. The `outcome-forecast` category checks forecastWeight curves on both metric and objective contributions, ordered by state or pattern-view `seq`: a weight that decreases as the curve progresses is an error, since a forecast cannot lose confidence; a weight of 1.0 *before* the recognised point, or a recognised point not weighted 1.0, are warnings. Weights after the recognised point are deliberately not flagged — holding 1.0 once recognised is correct. `--brief` prints the one-line form `validate-practice.py --brief` already uses, plus the detected kind and suggested mode; `--summary` gives the compact JSON with per-category counts. Both exist because the full report is tens of thousands of tokens and an agent that only wants the headline figure will otherwise reach for an inline script to extract it — one §7 breach in the October regeneration run was exactly that | `python3 utils/assess-practice.py <file>.json [--baseline <baseline>.json] [--schema <schema>.json] [--parent <parent>.json] [--brief] [--summary] [--errors-only] [--category CAT [CAT ...]] [--online]` |
| `scan-corpus.py` | Run `assess-practice.py` over every authored document and report where an issue category occurs. Answers the question triage asks that a single-document assessment cannot — a defect was found here, where else does it occur? Skips backup directories, `.changerequest.json` files and underscore-prefixed build artifacts, so a hand-written loop does not have to remember to. Resolves each document's baseline and dependency practices first (via `discover-dependencies.py`), since without them every symbolic reference into the baseline reads as dangling; where resolution is incomplete, cross-reference categories are **suppressed and counted** rather than reported, because a false dangling reference is worse than a gap. `--no-resolve` skips resolution and is much faster, appropriate for self-contained categories such as `uniqueness`, `outcome-forecast` and `counts`; `--include-unresolved` forces cross-reference findings through and will produce false positives. `--validator` runs `validate-practice-json.py` / `validate-baseline-json.py` instead of the assessment: the two check different things, and only the assessment reached this sweep, so error classes the validator owns were invisible to the tool triage uses — 57 ambiguous pattern views across 11 documents had accumulated against a rule the validator has always called an error. The `--validator` path passes **every** resolved baseline, not just the nearest: it used to hand the validator `baselines[0]` alone and drop the ancestors the resolver had just walked, which made the sweep manufacture the cross-reference phantoms it exists to find — a corpus run returned **1,271 findings across 30 documents** where the correct figure is **109 across 10**, and the 1,160 `baseline` findings named competencies, alphas and narrative types that are all declared in the dropped parent. `crossRefSuppressedFor` read `[]` throughout, so the guard for incomplete context never fired on context that was being discarded after resolution rather than failing to resolve. Documents whose `kind` is not a practice, method or baseline are skipped rather than counted unreadable. Exits 1 when anything matches, so it can gate. `--compare <before>.json` answers the other question — a change was made to a prompt, a utility or the resolver, did it introduce anything? It diffs against an earlier `--json` report by document *and* category, because a total that happens to match can hide one defect traded for another, and exits 1 only where a document gained findings | `python3 utils/scan-corpus.py [--category CAT [CAT ...]] [--severity error\|warning] [--dir DIR ...] [--schema <schema>.json] [--no-resolve] [--include-unresolved] [--json]` <br> `python3 utils/scan-corpus.py --json > before.json` … `python3 utils/scan-corpus.py --compare before.json` |
| `audit-method-references.py` | Cross-practice reference auditing within a method (alpha refs, duplicates, persona consistency). Accepts a method JSON, a directory of practice JSONs, or a `.keleo` bundle. **Pass the documents' own baseline — the leaf, not the root.** The baseline given to `--baseline` has its own ancestors merged in before the audit runs, so the leaf reaches the whole chain and the root does not reach its descendants. The tool used to read the leaf alone: over 18 members of one method it reported **22 errors** given `Partner Ecosystem Essentials` and **0** given its parent `Red Hat Sales Essentials`, with phantoms (`Customer Success`, `Technical Validation`, `Solution Fit`) indistinguishable from the cross-practice collisions the tool exists to find; both now give 0. The fix inverts which argument is wrong rather than making the choice free — on a method whose members sit under the extension baseline, the **root** now produces the phantoms (2 errors against 0) because it has never heard of its own descendants | `python3 utils/audit-method-references.py <method>.json \| <dir>/ \| <bundle>.keleo --baseline <baseline>.json [--json]` |
| `audit-bundle-freshness.py` | Detect `.keleo` bundles carrying stale embedded copies of documents that have since been fixed on disk. Compares each bundled document's version against the highest on-disk version of the same name and reports drift, so corrected content (renamed elements, removed aliases) cannot be reintroduced by an un-rebuilt bundle. Exits 1 when any stale copy is found. `--rebuild` repackages drifted bundles from current on-disk sources and bumps the manifest version (prerelease suffixes preserved); documents that exist only inside the bundle — typically externalized method documents generated at packaging time — are carried over verbatim. Naming bundles with `--bundle` forces their rebuild whether stale or not. **A rebuild that writes requires an explicit scope** — `--bundle`, `--document`, or `--all` — and without one it refuses, naming every bundle it would have touched. The audit defaults to the whole corpus, so an unscoped `--rebuild --fix` inherits that breadth: the command that repackages one practice's bundle after updating it is character-for-character the command that repackages every drifted bundle in the project, and the breadth was only visible in the output after the archives had been replaced. Dry runs stay unscoped, because surveying the corpus costs nothing and the survey is the point. A plain `--rebuild` refuses a bundle whose entry point declares dependencies the archive does not hold, because repackaging that set would certify an archive that cannot resolve itself; `--reclose` closes the gap instead, pulling those documents from `deps/`, `baselines/` and `practices/` transitively, since a document added to close one gap may declare dependencies of its own. Added documents sort ahead of the manifest's own, and deeper waves ahead of shallower, so the entry point stays the entry point — `package-keleo.py` takes the last document where no method is present, and appending a dependency to a practice bundle would otherwise make that dependency the entry point | `python3 utils/audit-bundle-freshness.py [--bundle <b>.keleo ...] [--document "Name" ...] [--stale-only] [--json]` <br> `python3 utils/audit-bundle-freshness.py --rebuild [--reclose] [--bump patch\|minor\|major\|none] [--fix --bundle <b>.keleo \| --fix --all]` |
| `validate-practice-json.py` | Schema validation for practices/methods | `python3 utils/validate-practice-json.py <file>.json` |
| `validate-baseline-json.py` | Schema validation for baselines | `python3 utils/validate-baseline-json.py <file>.json` |
| `check-root-dispatch.py` | Report which root `$defs` type the schema's dispatcher selects for a document, and flag any document where that disagrees with its `kind`. The root is a chain of `if`/`then`/`else` branches routing on the **presence of properties**, not on `kind`, so a document whose property set and `kind` disagree validates clean against entirely the wrong shape — the known case is a baseline declaring the singular `baselinePracticeName` instead of the array `baselinePracticeNames`, which routes to `#/$defs/Practice` and silently disapplies every baseline constraint. Validation reporting `valid: true` says nothing here, which is why this is a separate check. `--dir` sweeps a tree; exits 1 when anything is misrouted | `python3 utils/check-root-dispatch.py <file>.json [...] [--schema S] [--json]` <br> `python3 utils/check-root-dispatch.py --dir baselines --dir practices` |
| `validate-phase-output.py` | Validate Phase 1/1.5/2 markdown output structure; `--one-line` prints a single-line verdict instead of the full JSON check list; `--check NAME` reports only the named checks (repeatable, prefix match), so one check's findings do not have to be dug out of the full list; `--source-manifest` checks every source document in an `extract-html-text.py` manifest (or newline-delimited source list) is actually drawn on, searching all given files — catches guides that fall between parallel cluster analysts; `--against-json` compares the output's pattern and view inventory against the generated JSON and reports where they disagree — a pattern described and never generated, a view generated and never described. The markdown is what anyone reads to understand why a practice looks the way it does and the JSON is what ships, so a reference authored from the prose will not resolve once they part company. Advisory, since the prose legitimately describes candidates that were later rejected; what matters is that the difference exists and was not recorded. With `--validate-patterns` each pattern is judged on its own views and its own alphas rather than on the guide's pooled set, and `pattern_prerequisite_order` applies pattern-completeness.md Pass 5 to the markdown — a view asserting a state whose `background.alphaStates` the pattern only reaches later — so the ordering is settled before Phase 3 renders it. Only prerequisites naming alphas the guide itself declares are judged, since the markdown cannot see the effective context. `--kind` selects the document shape being validated: `practice` (default), `baseline`, `method`, or `orchestration` — `baseline` and `method` declare no patterns, work products or activities, so those section and pattern-view checks are skipped rather than failing a guide that is correct. `orchestration` is for a host practice that sequences the patterns of its dependencies: it owns a pattern, a `patternOrchestration` and a few coordinating activities, but no alphas and no work products of its own, so those counts measure nothing and the activity floor drops to 1. Without it such a guide fails `alpha_count` and `work_product_count` as *critical* for being correctly shaped | `python3 utils/validate-phase-output.py <file>.md --phase <1\|1.5\|2> [--kind practice\|baseline\|method\|orchestration] [--validate-patterns] [--against-json <practice>.json] [--gate] [--one-line] [--stats] [--source-manifest <manifest>.json]` |
| `normalize-guide-refs.py` | Strip code-span backticks from the labelled symbolic-reference fields of a phase guide (`Alpha Name`, `State Name`, `Work Product Name`, `Level Of Detail Name`, `Pattern Name`, `Competency Name` and the rest). A mapping guide is prose, so authors reasonably backtick element names — but `validate-phase-output.py` extracts the value literally, so a pattern view reading ``Alpha Name: `X` `` yields the name with its backticks and never matches the name taken from the `#### Alpha: X` heading. The guide then fails `alpha_pattern_coverage` with "0/N alphas take part in at least one pattern", which is a confident, wrong finding about a guide whose patterns are complete; the same literal copy reaching Phase 3 is a dangling reference in a JSON string. Prose, headings, tables and backticks inside narrative text are untouched, because there the code span is doing its job. Idempotent; exits 1 in dry run if anything would change | `python3 utils/normalize-guide-refs.py <guide>.md [--fix] [--json]` <br> `python3 utils/normalize-guide-refs.py --dir practices/<unit> --fix` |
| `verify-mapping-against-specs.py` | Verify Phase 2 mapping output against Gherkin specs. Accepts alpha sections at h3–h6 and activities as either a bold run-in label or an h3–h6 heading — all forms are in active use across the library. Check `extracted.alphaCount` is non-zero before trusting a pass: a guide the extractor cannot parse reports no findings, which looks identical to a clean run | `python3 utils/verify-mapping-against-specs.py <mapping>.md --baseline <baseline>.json [--parent <parent>.json] [--kind baseline]` |
| `eval-skill-output.py` | Evaluate skill output quality against assertions; auto-discovers baseline, parent practices, and schema; `--errors-only` filters to error-severity (excludes warnings). `--selftest` proves each assertion catches a planted defect, using `tests/fixtures/practice-good.json` and the mutation catalogue in `tests/mutations.py` — offline, no API. It reports `UNCOVERED` assertions (nothing proves they can fail) and gates `--evals`, which refuses to score a batch on an unproven grader unless `--no-selftest` is passed | `python3 utils/eval-skill-output.py <practice-dir> [--specs <specs-index.json>] [--one-line] [--errors-only]` <br> `python3 utils/eval-skill-output.py --selftest [--verbose]` |
| `run-skill-eval.py` | Run a skill's eval cases with and without the skill, in isolated workspaces, and report the delta. Cells run in a temp directory outside any git repo with `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` and `--setting-sources project,local`, because a no-skill arm that still reads the project CLAUDE.md measures nothing. `--selftest` proves the isolation and that each contaminant is actually detected; it gates every run. Workspaces are kept so `--rescore` re-grades offline after an assertion changes. **A cell is a full skill run and costs real money** — start with `--dry-run`, then one `--case` and `--runs 1` | `python3 utils/run-skill-eval.py --selftest` <br> `python3 utils/run-skill-eval.py --evals <evals.json> --case <id> --dry-run` <br> `python3 utils/run-skill-eval.py --evals <evals.json> --case <id> --arms with-skill,without-skill --runs 1` <br> `python3 utils/run-skill-eval.py --rescore runs/<stamp>` |
| `lint-practice.py` | Combined validate-fix-revalidate loop (auto-discovers baseline/schema) | `python3 utils/lint-practice.py <practice>.json [--fix] [--one-line] [--max-iterations N]` |
| `lint-report.py` | Verify generated markdown reports before handover: Keleo vocabulary leaks (@rule:report-600), bidirectional in-text ↔ `## References` citation correspondence with surname matching (@rule:report-607/608), framework names in the closing attribution line rendered as keleo-studio-gas deep links (@rule:report-610), diagrams rendered as SVG rather than ASCII art with alt text and a resolvable target (@rule:report-611/612), professional register — variables given agency over decisions, rhetorical or contrarian headings, and editorialising phrases such as "works on paper" (@rule:report-619, warnings only, since each is context-dependent) — framing prose before a section's first subsection, table or figure so a reader does not meet `### Option A` without knowing B and C exist (@rule:report-618, tunable with `--min-section-words`, skips `00-prompt-history.md`), over-repeated contrast constructions — "rather than", "instead of", "X, not Y", "not X but Y", "X and not Y" — counted per thousand body words, per form and in total (@rule:report-619, warnings only). The total is the one that matters: this check exists because a human reviewer caught 23 instances of "rather than" in one 4,264-word report, and rewriting them spread the same habit across four forms instead of removing it, which a per-form threshold alone misses. Both a rate and a minimum count must clear, so a few contrasts in a long report stay silent. `--selftest` proves the check fires on monotone prose and not on varied prose, with no files and no network. Also body word count against the target band, and a heading outline for checking the narrative mapping. Citation matching recognises all four in-text forms the reporting foundation prescribes: parenthetical `(Author, 2024)`, hyperlinked parenthetical `([Author, 2024](url))`, narrative `Author (2024)`, and hyperlinked narrative `[Author (2024)](url)`. Accepts several reports at once; with `--consistent-terms` it also checks that fixed names (play, TDP, tactic, product) are used identically across the whole set. Exits 1 on any error | `python3 utils/lint-report.py <report>.md [<report>.md ...] [--checks terminology citations diagrams attribution length structure sections tone cadence] [--consistent-terms "Name A" "Name B"] [--min-words N --max-words N] [--min-citations N --max-citations N] [--studio-url URL] [--strict] [--json]` <br> `python3 utils/lint-report.py --selftest` |
| `check-pattern-prerequisites.py` | Check pattern views against the alpha-state prerequisite graph. A view asserting a state whose own `background.alphaStates` the pattern only reaches at a later view is an inversion — the pattern claims the state holds before the document says it can. Also flags a state that goes backwards across views. Prerequisites are merged across every document passed, because state redeclaration is additive, so a practice alone shows only what one document can prove while the practice plus its baseline and dependencies shows the real graph. A later state of the same alpha satisfies an earlier one. Prerequisites on alphas the pattern does not carry are reported as `unreached` rather than inverted, since view compression makes that ordinary. Three further orderings look like inversions and are named rather than reported as defects: `entry`, where the pattern's first view states conditions met before it begins (§9.2 rule 3) — `--strict-entry` judges that view like any other; `cyclical`, where a `loopsBackTo` span means the prerequisite was reached on an earlier lap and a re-entered state is the minimum for that pass (§9.2a.1); and `ambiguous`, where a view declares one alpha twice, which only makes the walk appear to move backwards — the ambiguity is reported and the regression it implies is suppressed, so one kind of defect does not hide behind another. `--variant-smell` asks a question rather than reporting a defect: an alpha whose states name kinds of the thing rather than stages of it cannot be walked monotonically by any pattern, and since remodelling it reaches every dependent document the call belongs to mapping. `--matrix` prints the view-by-view state grid for checking a prose record against the JSON. Exits 1 on an inversion, a regression or an ambiguous view. `tests/check-prerequisite-classification.py` holds these distinctions against a fixture, because the corpus cannot exercise them — one practice declares a loop and it has no finding inside it. `assess-practice.py` imports this module for its `pattern-prerequisites` category (@rule:coverage-006), so the same rule reaches `scan-corpus.py`; run the script directly when you want the matrix or the `unreached` findings the assessment drops. `--cycles` asks a different question of the same graph: two practices on one baseline can declare opposing prerequisites between the same pair of states, and since redeclaration is additive the contradiction exists only in the union — each document validates clean holding half of it, and it surfaces only when someone declares a dependency and inherits the failure. **`--cycles` is additive, not exclusive**: it used to `return` before the view walk, so the merged command this project prescribes (`--cycles --implicit-order --strict-entry --variant-smell`) answered the cycle question, skipped every view check the other three flags configure, and printed a clean line about something it had never looked at. Both questions now run; `--json` then emits `{"cycles": [...], "findings": [...]}` rather than a bare findings array, and the exit code is 1 if either question fails. `--on-baseline` still short-circuits, because a corpus sweep has no single pattern owner to walk views against. `--on-baseline "<Name>"` sweeps every corpus document whose baseline chain reaches that baseline, transitively, and names the document that declared each edge of a cycle. `--implicit-order` adds the sequential edge every alpha carries between consecutive states, which the documents never write down: a `background.alphaStates` graph can be acyclic on its declared edges alone and still deadlock once state order is present, and that is the graph a reader has to satisfy. The baseline and practice validators check the declared edges only, so this is the stronger reading | `python3 utils/check-pattern-prerequisites.py <practice>.json [<baseline>.json <dep>.json ...] [--pattern "Name"] [--matrix] [--json]` <br> `python3 utils/check-pattern-prerequisites.py --cycles --on-baseline "<Baseline Name>" [--json]` |
| `post-validate-method.py` | Batch fix-validate pipeline for extension practices; skips baselines, methods and working JSON, counts skipped files, and fails visibly on unreadable inputs or failed subprocess reports. Optional cross-practice audit errors contribute to the aggregate error count | `python3 utils/post-validate-method.py <directory>/ [--fix] [--one-line] [--audit] [--baseline <baseline>.json]` |
| `verification-gate.py` | Consolidate the findings of a stage's verification agents and gate on them. `--phase` takes a generation phase (`1`, `1.5`, `2`, `3`) or `report` for the reporting skills' single gate, which writes `report-<verifier>.json` rather than `phase-<N>-<verifier>.json`. Reads `<dir>/_verification/phase-<N>-<verifier>.json`, dedupes across verifiers keeping the highest severity, applies the reconciler's per-finding verdicts from `phase-<N>-reconcile.json`, and writes `phase-<N>-verdict.json` plus a markdown summary for the user review gate. `--gate` exits 1 when a blocking error survives. **Always pass `--expect`** — without it a verifier that crashed before writing its file is indistinguishable from one that found nothing, and the gate passes on silence. `--path-for` prints the path a named verifier should write to. Purely mechanical: deciding whether a finding is real stays with the reconciliation agent. See `.claude/skills/verification-foundation/` | `python3 utils/verification-gate.py <dir>/ --phase <1\|1.5\|2\|3\|report> --gate --summary --expect <v1>,<v2>` <br> `python3 utils/verification-gate.py <dir>/ --phase 2 --path-for source-fidelity` <br> `python3 utils/verification-gate.py --selftest` |
| `calibrate-verifiers.py` | Prove a verification agent catches the defect it exists to catch, by running it against a matched clean/defective pair in `tests/calibration/`. Passing requires both: no finding on the clean artifact, and a finding that *names* the planted defect on the other. The prompt is extracted from the live brief, so rewording a brief invalidates its calibration. `--check` is offline and lists stale and missing calibrations; `verification-gate.py` reads the results and adds an info finding for any uncalibrated verifier at that gate, without blocking. See `.claude/skills/verification-foundation/` §11a | `python3 utils/calibrate-verifiers.py --check` <br> `python3 utils/calibrate-verifiers.py --verifier source-fidelity --phase 2` <br> `python3 utils/calibrate-verifiers.py --all` |

### Automatic interaction capture

`prompt-history.py --init` writes `.tmp/active-prompt-history.json`, which points two hooks in
`.claude/settings.json` at the live history:

| Hook | Records |
|------|---------|
| `UserPromptSubmit` → `--hook user-prompt` | Every user turn, verbatim, under `## Interaction Log` |
| `PostToolUse` matching `AskUserQuestion` → `--hook tool` | The question(s) put to the user and the option(s) they chose |

The pointer binds to the first session that fires, so a concurrent session in this project
cannot leak its prompts into the history. `--finalize` clears the pointer; `--activate`
re-arms it when resuming an existing practice in a new session. Hook mode never writes to
stdout and always exits 0 — a recording failure must not break the session.

The hooks capture what the user *said*. A question asked in plain prose, outside
`AskUserQuestion`, still needs `--add-interaction` so the question is recorded alongside the
answer.

**`.claude/settings.json` is git-ignored**, so a fresh clone has no hooks. Re-add the two
entries above to enable automatic capture.

## Tooling feedback checks

The 1.1.0 assessment, scan and sync utilities add these checks; the bundle auditor is
1.2.0 and the batch validator and grader fixes are 1.0.1.

- `assess-practice.py` accepts pattern-view or orchestration-stage objective contributions. Stage references resolve against merged placements, including their hosts; sequential forecast curves cannot decrease. The summary and extraction utilities preserve both contribution shapes.
- Assessment reports `dependency-version` warnings against loaded dependencies. Bundle audits report `versionFindings` for embedded documents and available external packages. The range evaluator reuses the language validator: exact, caret, tilde and comparator ranges are supported; unsupported syntax is reported rather than treated as satisfied. Review constraints before running `apply-versioning.py <file> --refresh-deps --fix`.
- `audit-bundle-freshness.py` compares parsed JSON at equal versions and reports `content-differs`. These copies qualify for an explicitly scoped rebuild; audit mode writes nothing.
- `scan-corpus.py` reports `documentsFailed` and `scanFailures`, distinguishes timeouts and unreadable output, and exits nonzero for scan failures even under category filters or comparison mode.
- The grader selftest uses the tracked, self-contained `tests/fixtures/selftest-baseline.json`. A mutation planting a valid baseline value is reported as unusable, separately from a grader missing a defect. Run `python3 tests/check-feedback-regressions.py` for focused regressions.
