# Diagram Guide

Version: 2.0.0

How to produce diagrams for reports. Read this at Step 2, when the practice context is resolved and
you are deciding what the report will show — not at Step 3 when you are already writing prose around
a gap.

Diagrams are **rendered SVG**, generated by `utils/render-diagram.py` from a JSON spec, or by
`utils/derive-diagram.py` from the practice itself. Never hand-draw ASCII art, and never hand-write
SVG geometry — `lint-report.py --checks diagrams` fails the report on the first, and the second
produces overlapping boxes and clipped labels.

The engine is shared with the deck skills.
`.claude/skills/diagram-foundation/DIAGRAM-FOUNDATION.md` carries the design tokens and the
rationale; this guide covers only what a report author needs.

---

## How many diagrams

A section that makes a **structural claim** earns a figure. Structural means components and the
connections between them, a sequence with dependencies, a containment hierarchy, or a progression
through stages. If the claim can only be made properly by naming the parts and how they join, the
prose is doing a diagram's job badly.

A section whose content is **comparative or quantitative** gets a table instead. Options scored
across dimensions, capacity figures, node counts, pricing — a diagram of these is a table with
rounded corners.

| Content | Use |
|---|---|
| Components and how they connect | `flow` |
| Layers resting on one another | `stack` |
| Phases in order, with dependencies | `timeline` |
| One thing related to several others | `hub` |
| Two axes crossed, or a completeness audit | `matrix` |
| Evidence feeding a measurable result | `flow` |
| Teams and the roles within them | `flow` |
| Who does what, in order | `swimlane` |
| Build versus buy, commoditisation | `wardley` |
| Options scored across dimensions | Table |
| Capacity figures, node counts, sizing | Table |
| A list of three things | Prose or a list |

In practice a standard report carries four to eight figures and a comprehensive one more. There is
no cap — but there is no quota either. A figure that restates its own caption should be cut.

## Layouts

| Layout | Shape | Reach for it when |
|---|---|---|
| `flow` | Layered boxes, directed edges, nestable cluster groups | Topologies, pipelines, data paths, cloud containment. The default |
| `stack` | Vertical tiers | Layer models, maturity stacks, architecture tiers |
| `timeline` | Sequential phase bands joined by arrows | Roadmaps, adoption journeys, phased rollouts |
| `hub` | Centre node with satellites on an ellipse | Relationship maps, integration fan-out |
| `matrix` | Grid with row and column headers | Capability heat maps, pace layering, Zachman, 2×2s, coverage audits |
| `wardley` | Components on a value-chain / evolution grid | Build versus buy, spotting commoditisation |
| `swimlane` | Lanes of steps with handoffs between them | Process modelling where who does what is the point |
| `canvas` | Left-to-right timeline of coloured stickies | Event Storming |

Any node may carry a `shape` (`rounded`, `rect`, `stadium`, `cylinder`, `hexagon`, `diamond`,
`event`, `note`, `sticky`, `person`), an `emphasis` (`default`, `muted`, `accent`, `selected`) or a
semantic `role` (`heat.1`–`heat.5`, `storm.*`, `evolution.*`, `pace.*`). Any edge may carry a `dash`
and an `arrow`. What each one *means* is in
`.claude/skills/diagram-foundation/references/visual-language.md` — read it before inventing a
convention.

Run `python3 utils/render-diagram.py --spec-help` for the full field reference. Do not inline that
output into a subagent prompt — point the agent at the command.

### Choosing a method, not just a layout

For anything with an established notation — C4, ERD, sequence, state machine, Event Storming,
Wardley — the selection matrix is
`.claude/skills/diagram-foundation/references/method-catalogue.md`. It names fifteen methods, their
audiences, which of them this engine produces, and which to decline and hand to another tool. Load
one `methods/<slug>.md` page afterwards, not all of them.

Its two warnings are worth carrying into every report: a formal notation imposed on an audience that
cannot read it loses the audience, and an informal drawing standing in for a specification gets
filled in by guesswork.

### Mermaid specs

A spec can also be a `.mmd` file — YAML frontmatter, then Mermaid source — rendered by the same
`render-diagram.py` call.

```
---
method: c4-container
title: Platform containers
description: Deployable units and the protocols between them.
render: scene
---
flowchart TB
  web[Web app]:::accent --> api[API service]
  api --> db[(Document store)]
```

`render: scene` lets Mermaid lay the graph out and then redraws every node in house shapes, so it
matches the native layouts exactly. Only a flowchart can do this. A `sequenceDiagram`, `erDiagram`,
`classDiagram` or `stateDiagram` keeps Mermaid's own picture, themed to the palette, and the renderer
says so — which is the right outcome, because lifelines and attribute compartments have no house
equivalent.

Mermaid needs `npx` on PATH; mermaid-cli is fetched on demand, pinned to v12. If it is missing, the
renderer says so and the diagram has to be authored as a native `.json` spec instead.

## Diagram material in the practice

A practice is not a document that happens to contain diagrammable facts. It is a **typed graph**,
and each relationship type in the language has a diagram shape that fits it. Work out which
semantic relation the section is actually talking about, and the method follows from it. That is the
whole strategy; the DR example further down is one instance of it, not the point.

| Language relation | What it asserts | Shape it wants | `--view` |
|---|---|---|---|
| `Alpha.relatesTo` (verb + direction) | These concerns act on one another | Graph | `concern-map`, `concern-hub` |
| `Alpha.contributesTo` / `mapsTo` | This concern specialises that one | Rollup tree | `capability-tree` |
| `Alpha.states` (ordered) | This concern matures through stages | Stack | `maturity` |
| `WorkProduct.contributesToAlphaNames` | This artifact evidences that concern | Bipartite graph | `evidence-map` |
| `WorkProduct.partOf` | This artifact is part of that one | Containment | `evidence-map` groups |
| `Pattern.patternViews` (by `seq`) | Work proceeds in these phases | Timeline | `journey` |
| `PatternView.alphaStates` | This phase advances that concern to that state | Grid | `pattern-matrix` |
| `Outcome.metricContributions` / `objectiveContributions` | This evidence, at this state, counts towards that value | Chain | `outcome-chain` |
| `PersonaGroup.personaNames` / `personaGroupNames` | These roles make up that team | Tree | `role-map` |
| `Competency.levels` | This capability looks like this at each level | Rubric grid | `competency-matrix` |
| `Focus` | These concerns belong to the same lens | Cluster groups | applied by `concern-map` |

Three relations carry structure the tool does not yet derive, because the contexts here do not
populate them: `State.contributesToState` (a child state advancing a parent state — a cross-level
`flow`), `LevelOfDetail.contributesTo` (evidence at state rather than concern granularity — a finer
`evidence-map`), and `Activity.ledBy` with `ActivitySpace` (who performs what, in order — a
`swimlane`). Where a context does populate them, author the spec by hand from the same reasoning.

Two relations deliberately have no diagram. `Checklist` and `Test` (`given`/`when`/`then`) are
verification criteria — a list or a table, never boxes.

**Start with discovery.** It prints the focuses, the alphas ranked by relationship count, the
patterns and their phase sequence, and the work products — which is how you pick a view and a scope
without reading a large JSON:

```bash
python3 utils/derive-diagram.py /tmp/report-context.json --list
```

**Then derive, scope, and edit.** A derived spec is a starting point, not an output. Rename nodes
into the subject's own language, drop what the report does not discuss, add anything the practice
does not carry:

```bash
python3 utils/derive-diagram.py /tmp/report-context.json --view concern-hub \
  --seed "VM Resilience" --out-dir reports/<slug>/assets/ --name resilience-context

python3 utils/derive-diagram.py /tmp/report-context.json --view journey \
  --pattern "Disaster Recovery Establishment Journey" \
  --out-dir reports/<slug>/assets/ --name dr-journey
```

Scope with `--seed`/`--depth`, `--focus` or `--practice`. The tool pushes back in three ways, all of
them worth listening to:

- **Node budget.** It refuses more than nine nodes and names the alphas that make the best seeds. A
  42-node relationship graph is a hairball, not a diagram.
- **Density.** Past roughly 1.8 edges per node a layered flow collapses into a single column and
  stops drawing edges where they belong — a wrong diagram, not merely a crowded one. It refuses, and
  points at `concern-hub`, which draws a star as a star. `--allow-dense` overrides it when you mean
  to rewrite the spec by hand.
- **Label crowding.** Three or more labelled edges meeting at one node put their labels on the same
  line. It says which node, and `--no-edge-labels` is usually the answer.

A seeded `concern-map` tends to string out into a tall chain, because a neighbourhood is a star and
the layered layout is not. `concern-hub` is almost always the better view for one concern in
context; keep `concern-map` for a cross-section scoped by `--focus` or `--practice`.

Two things the derivation **cannot** do, because they are judgment rather than data: deciding which
figure a section needs, and translating the practice's internal vocabulary into the subject's. A
derived node labelled "Platform Consumption Interface" must not reach the reader under that name
(@rule:report-600).

## Types and instances

The language draws this distinction itself, and it is the single most useful thing it gives a report
author. `Alpha` and `WorkProduct` are **types** — the concerns and artifacts a practice says exist
in its domain. `AlphaInstance` and `WorkProductInstance` are **occurrences** of those types in one
real situation, each at its own state, each able to relate to other occurrences through
`InstanceRelationship` — a relation that exists between two particular things and not between their
types.

A practice is written at the type level. A report is always about one situation, and a situation
routinely contains several occurrences of something the practice names once:

| The practice names once | The situation has |
|---|---|
| Platform | A production platform and a disaster recovery platform |
| Platform Infrastructure | A cluster per region, or per sovereignty boundary |
| Team | A platform team and three stream-aligned teams, each at a different Way of Working state |
| Environment-scoped concerns | Development, staging and production, diverging in maturity |
| Requirements | One set per tenant on a shared platform |

In every one of those, drawing the type collapses the thing the report exists to say. The two
clusters are not one cluster; the gap between the production team's maturity and the others' is the
finding. So: **draw the occurrences, not the type.**

- Name each instance in the subject's own words — "Production site", "DR site", "Frankfurt cluster"
  — and put the practice concern in the `sublabel`, so the figure stays traceable without leaking
  vocabulary into the label.
- Each instance inherits the type's relationships. If the practice says operational assurance
  validates the infrastructure, it validates both sites.
- The interesting edges are the ones **between** instances — "replicates to", "fails over to",
  "promotes on failure". These are not in the practice. Write them into the spec yourself.
- Instances of the same type can be at different states. Production is "Resilience Proven" while DR
  is "HA Configured"; that gap is often the report's whole point, and a `matrix` of instances against
  states says it better than prose.

`derive-diagram.py` does the node expansion:

```bash
python3 utils/derive-diagram.py /tmp/report-context.json --view concern-map \
  --practice "Disconnected OpenShift" \
  --instance "Disconnected Cluster Provisioning=Production cluster,DR cluster" \
  --no-edge-labels --out-dir reports/<slug>/assets/ --name dr-topology
```

Then open the emitted spec and add the edge the practice could not know about:

```json
{"from": "production-cluster", "to": "dr-cluster", "label": "replicates to", "dash": "dashed"}
```

`--instance` applies to the `flow` views — `concern-map`, `capability-tree`, `evidence-map`,
`outcome-chain`, `role-map`. A `hub` has one centre, so split its satellites by hand. Splitting a
node adds edges as well as boxes, so it counts against the node budget and often trips the density
check; that is a signal to narrow the scope, not to raise the budget.

A report that models its instances this way has done the thinking a Keleo `Project` document
records. It should not produce one — but the modelling carries over if someone later does.

## Workflow

**1. Pick the figures at Step 2**, while the domain knowledge is in front of you. Run
`derive-diagram.py --list` and note which sections will carry which view.

**2. Write or derive the spec** into the report's assets directory:

```
reports/<report-slug>/
  <report-slug>.md
  assets/
    dr-topology.json
    dr-topology.svg
```

The spec is kept, not discarded — it is how the diagram gets corrected later without redrawing it,
and how the same figure reaches a slide as editable shapes.

**3. Render every spec in one call** once they are all written:

```bash
python3 utils/render-diagram.py --dir reports/<report-slug>/assets/
```

Batch mode writes each `<name>.svg` beside its `<name>.json`. One call per report, not one per
diagram.

**4. Embed with a relative path, real alt text, and a numbered caption:**

```markdown
![Production and DR sites share one operational assurance regime but sit at different resilience states](assets/dr-topology.svg)

*Figure 1 — Production and disaster recovery topology*
```

The caption carries the spec's `title`, which is otherwise invisible to a sighted reader — the SVG
does not draw it. Where a heading immediately above already names the figure, do not echo it; name
what the figure *shows* instead.

Number figures sequentially through the report so prose can refer to "Figure 2" instead of "the
diagram above", which breaks as soon as a page boundary moves.

The caption and the alt text do different jobs and should not be the same sentence. The caption
**names** the figure; the alt text states its **claim**, for a reader who cannot see it.

**5. Look at the rendered pictures before handing over:**

```bash
python3 utils/preview-diagram.py --report reports/<report-slug>/<report-slug>.md
```

Clipped labels, colliding edge labels and overlapping cluster rects are invisible to a validator and
obvious in a raster. Do not substitute macOS `qlmanage -t` — it crops tall diagrams silently, so a
broken figure reads as a clean one.

Because the report carries its own captions, do **not** publish it to Google Docs with
`publish-doc.py --captions` — that renders the alt text as a second caption under the same figure.
Alt text reaches the Doc as the image description either way.

## Writing a good spec

**The title is not drawn.** `title` and `description` become the SVG's `<title>` and
`<desc>`/`aria-label` — metadata for screen readers, never artwork. The markdown caption beneath the
figure names it, so a rendered title would print the same line twice. Set both fields anyway:
`title` is the caption text, and both are what a non-sighted reader gets.

**Labels are noun phrases, not sentences.** "Automation controller", not "The automation controller
runs scheduled scans". Detail belongs in `sublabel` or in the prose around the diagram.

**Three to nine nodes.** Below three, prose is clearer. Above nine, split the diagram or raise its
level of abstraction. A diagram that will not fit is usually a diagram carrying more than one idea.

**Use `emphasis` sparingly.** One or two `accent` nodes draw the eye to what matters; everything
accented is nothing accented. `muted` recedes a node that is context rather than subject.

**Label the edges that carry meaning.** "scheduled scan" earns its place; "connects to" does not, and
the same label repeated on every edge is noise that collides with itself.

**Group when containment is part of the point** — a trust boundary, a network zone, a vendor
boundary. Not merely to tidy the layout, and not when there is only one group.

**The diagram supplements the prose, it does not replace it.** A reader who cannot see images must
still follow the argument.

## Styling

The visual language comes from the keleo-studio-gas navigator, so reports, the studio UI and the deck
theme read as one system. Tokens live in the `THEME` dict in
`.claude/skills/diagram-foundation/scripts/diagram.py` — change them there, never per-diagram. Specs
carry content and structure only; they do not set colours, fonts or sizes.

## Decks are different

The deck skills use the same engine but take a different route out of it — a diagram on a slide
becomes native Google Slides shapes, because SVG does not survive the PowerPoint to Google Slides
conversion (`deck-foundation/DECK-FOUNDATION.md` §"conversion safety"). The spec is what crosses
between them, which is why it is the artifact worth keeping. This guide's rendering and embedding
steps apply to reports only.
