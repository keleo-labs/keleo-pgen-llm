# C4 model

Route B (`flowchart`, `render: scene`), so it becomes editable Slides shapes.

## When

The default for documenting a software system. Four levels, and you pick one
per diagram — mixing levels in one picture is the commonest C4 mistake.

| Level | Shows | Audience | Draw it when |
|---|---|---|---|
| 1 Context | The system as one box, its users and the systems it talks to | Anyone, including non-technical | Establishing scope and who is affected |
| 2 Container | Deployable, runnable units and the protocols between them | Architects, ops, engineers | **The most useful single diagram most systems have** |
| 3 Component | Inside one container: controllers, services, gateways | Developers working in that codebase | A feature is about to land and the structure matters |
| 4 Code | Classes and inheritance | Nobody, by hand | Never — generate it or omit it |

A "container" is anything that executes code or stores data: a web app, an
API, a worker, a database, a queue. Not a Docker container, though it is
often also one.

## Notation

- One level per diagram. If you are tempted to show a component inside a
  container diagram, you need two diagrams.
- Every element says *what it is* and, at level 2, *what technology*. Put the
  technology in the label after a line break or in the node text.
- Every edge says *what flows and how*: "JSON over HTTPS", "reads from",
  "publishes order events". An unlabelled arrow at container level is a gap.
- People use `:::person`-style classes only if you have defined them; the
  house `accent` class is usually enough to mark the primary actor.
- A `subgraph` is a boundary — the system, or an enterprise edge.

## Spec

```
---
method: c4-container
title: Keleo Studio containers
description: Deployable units and the protocols between them.
render: scene
---
flowchart TB
  user[Account manager]:::accent
  subgraph studio["Keleo Studio"]
    web[Web app]
    api[API service]
    db[(Document store)]
  end
  sf[Salesforce]:::muted
  user --> web
  web -->|JSON over HTTPS| api
  api --> db
  api -.->|nightly sync| sf
```

Mermaid lays this out and the engine redraws it in house shapes, so it
becomes native Google Slides shapes like any hand-written spec.

## Mistakes this invites

- **Mixing levels.** The symptom is a diagram with both "Billing service" and
  "OrderRepository" in it.
- **Unlabelled edges at container level.** The protocol is half the content.
- **Drawing level 4.** It rots within a sprint. Generate on demand or leave
  it out.
- **Calling a context diagram a container diagram.** If internals are not
  shown, it is level 1, and saying so manages what the reader expects.
